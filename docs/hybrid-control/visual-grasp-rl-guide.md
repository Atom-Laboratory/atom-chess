# Visual grasp training — Windows user and developer guide

## Start and watch

Run PowerShell in the repository root. Use the existing fingertip-only Playground
bundle, generated by Start-MuJoCo.ps1 -Mode playground. Close other simulator
windows before training so their graphics and physics do not compete.

    & ./simulation/mujoco/scripts/Start-RLTraining.ps1 -Stage lift -Steps 20000 -Device cuda

Two windows open: the MuJoCo 3D scene and the exact 96x96 RGB policy image enlarged
for inspection. The policy camera stays fixed. Move the 3D inspection camera
without changing the policy image. The status shows steps, bilateral grip, lift,
success and disturbance. Use Pause training / Resume training or Stop and save
checkpoint. Closing either window stops training and saves the final checkpoint.
PPO optimizer updates can temporarily pause the animation. Viewer speed defaults
to 2x simulated control time; -Speed 1 is slower and -Headless removes UI pacing.
The 3D viewer is observational: its mouse perturbations are not applied to physics.

Each run creates a new directory under simulation/mujoco/runs and prints its path.
policy.zip is saved on completion or graceful stop; checkpoint-N.zip is saved
periodically. A forced process kill cannot guarantee a final save. Creating an empty STOP file
in the run directory also requests graceful stop at the next training step.
episodes.jsonl contains training episode results, progress.json is an atomic
status snapshot, run.json records the environment, and report.json contains
held-out evaluation after a normal finish. A stopped run skips evaluation and
cannot be interpreted as successful training. Training rate and held-out success
are different measures. No policy is automatically enabled for chess or hardware.

## Curricula and honest interpretation

Stage lift begins with a reset-only verified grip. The policy must learn to lift
and retain the piece without displacing neighbors. It does not learn closing.
Once held-out lifts are reliable, start a separate grasp run:

    & ./simulation/mujoco/scripts/Start-RLTraining.ps1 -Stage grasp -Steps 100000 -Device cuda

Stage grasp starts 20 mm above the proxy grasp point with fully open jaws. The reset rejects initial pad contact with the target. Older grasp reports without a grasp_reset field replay the historical pre-shaped reset. Actions are
bounded joint-reference increments for J1, Z, J2 and both coupled fingers. Both
stages operate on the E2 pawn with small randomized initial arm offsets. Rewards
and success use simulation oracle contacts, poses and bystander displacement;
policy inputs are RGB only. Version 3 uses potential differences and a terminal
bonus, so repeatedly holding at a partial lift is not rewarded every step. This is not generic source-to-destination transfer,
acvision-based verification, full-game learning or physical robot readiness.

Current acvision BoardDetector estimates board corners; it does not supply a
reliable held-piece/gripper pose. A fixed RGB policy can be trained without that
feature extractor. Real camera calibration, deployment observations, transfer
curricula and hardware execution remain separate work. ac:chess and the production
state store are not changed by these isolated training episodes. The existing
MotionController executes each learned target; reset staging uses legacy IK.

## Resume or replay

Use a new output directory when resuming; -Resume is a previous run directory:

    & ./simulation/mujoco/scripts/Start-RLTraining.ps1 -Stage lift -Steps 20000 -Device cuda -Resume PATH_TO_PREVIOUS_RUN
    & ./simulation/mujoco/.venv/Scripts/python.exe simulation/mujoco/examples/replay_visual_grasp.py --bundle simulation/mujoco/runs/playground-fingertip-only-v1 --run PATH_TO_RUN --seed 10000

Resume requires the same model hash, environment version, stage and horizon. It
restores policy and optimizer but not the exact previous physics state or rollout.
Steps means additional requested training steps. Old P023 checkpoints use a different
curriculum and must be replayed with their original code revision, not relabeled.

## Dependencies and GPU

    & ./simulation/mujoco/.venv/Scripts/python.exe -m pip install -e './simulation/mujoco[rl]'
    & ./simulation/mujoco/.venv/Scripts/python.exe -m pip install 'torch==2.14.1+cu130' --index-url https://download.pytorch.org/whl/cu130
    & ./simulation/mujoco/.venv/Scripts/python.exe -c "import torch; print(torch.__version__, torch.cuda.is_available()); print(torch.cuda.get_device_name(0))"

The CUDA command is the workstation-tested Windows wheel from the official
PyTorch index. GPU compute accelerates the policy, not standard MuJoCo dynamics.
Do not infer GPU usage from the installed graphics card alone. --device cuda
rejects unavailable CUDA; --device auto may select CPU. Tkinter and Pillow provide
the camera panel. See P025 for architectural context, alternatives and limitations.

## Developer verification

Run pytest on test_visual_grasp_env.py and test_training_monitor.py. These check
RGB shapes, invalid actions, deterministic resets, stage separation, a scripted
lift feasibility probe and durable metric records. The scripted probe is not
learned-policy evidence. Run a short actual PPO experiment to verify changed
weights, checkpoint reload, device selection, held-out evaluation and graceful
UI stop before making training claims.
## Transfer from lift to grasp

Start a new run with the saved lift policy:

    & ./simulation/mujoco/scripts/Start-RLTraining.ps1 -Stage grasp -Steps 100000 -Device cuda -WarmStart simulation/mujoco/runs/visual-lift-camera-v3-20000

Warm-start copies the policy, including the visual encoder and both heads.
The new optimizer and timestep counter start fresh. The source checkpoint
hash and stage are recorded in run.json and report.json. Use Resume for
continuing an identical task. This transfer requires the same model bundle,
environment version and horizon. Evaluate expanded collision geometry separately.
