# Homography experiment protocol

## Reproduce the historical nine views

These are nine sequential camera poses, generated by one MuJoCo MjvCamera.
The camera azimuth takes 265, 270 and 275 degrees. For each azimuth the
elevation takes -35, -45 and -55 degrees. Thus 3 x 3 = 9 images.
This is a viewpoint sweep. Multi-camera fusion has a separate experimental scope.

The P033 capture used the following configuration.

| Parameter | Value |
|---|---|
| Model bundle | simulation/mujoco/assets/bundles/playground-fingertip-only-v1 |
| Model file | model.xml inside the bundle |
| Scene metadata | manifest.json inside the bundle |
| Capture script | simulation/mujoco/examples/validate_native_perception/run.py |
| Renderer | mujoco.Renderer, 800 x 600 px |
| Camera | Free MjvCamera, configured by the capture script |
| lookat | [0.245, 0.0, 0.012] m, from manifest scene.board_center_m |
| distance | 0.85 m from camera to lookat |
| azimuths | 265, 270, 275 degrees |
| elevations | -35, -45, -55 degrees |
| vertical FOV | 45 degrees, recorded from model.vis.global_.fovy |
| Physics engine | MuJoCo 3.17.0 in the archived report |
| Native model SHA256 | 2b439e465a9f048ed49df4d681a965650a5a1347f728c2b04cba9c4a935b6b59 |

The free camera configuration lives in Python. Editing a named camera in XML
will not change this capture path. Distance is the radial distance to lookat,
rather than the camera height or horizontal mounting distance.

From the repository root, use the existing virtual environment.

~~~powershell
cmake --build build/p032-contract --config Release --target perception_image
$exe = (Resolve-Path build/p032-contract/bin/Release/perception_image.exe).Path
$run = Join-Path simulation/mujoco/runs ('p033-repeat-' + [guid]::NewGuid().ToString('N'))
& simulation/mujoco/.venv/Scripts/python.exe -B simulation/mujoco/examples/validate_native_perception/run.py --bundle simulation/mujoco/assets/bundles/playground-fingertip-only-v1 --executable $exe --output $run --azimuths 265 270 275
Invoke-Item (Join-Path $run 'lateral-270-45.png')
Invoke-Item (Join-Path $run 'report.json')
~~~

For one fixed pose, edit the script's elevation tuple to contain only -45,
and run with --azimuths 270. This is a manual experimental variation.
Without that edit, --azimuths 270 still captures three elevations.

The historical artifacts are in
simulation/mujoco/examples/validate_native_perception/runs/p033-viewpoint-sweep-20261106.
Successful views have rectified.png and rectified-grid.png in their
acvision-AZIMUTH-ELEVATION directories. Failed views retain corners.png
and observation.json. A successful current run reproduces the protocol.
Bitwise historical reproduction additionally requires the archived executable,
model/assets and runtime versions. The report records executable and model hashes.

## Reproduce the ArUco experiment

~~~powershell
$run = Join-Path simulation/mujoco/runs ('p034-repeat-' + [guid]::NewGuid().ToString('N'))
& simulation/mujoco/.venv/Scripts/python.exe -B simulation/mujoco/examples/validate_board_reference/run.py --bundle simulation/mujoco/assets/bundles/playground-fingertip-only-v1 --assets docs/camera-rl/aruco-assets-v4 --executable $exe --output $run
Invoke-Item (Join-Path $run 'initial-270-45/rectified-grid.png')
~~~

This script adds visual marker surfaces in a new reference-scene.xml in the
output directory. It renders 1920 x 1440 px with distance 1.05 m, azimuths
265/270/275 and default elevations -35/-45/-55. It uses initial, empty and
offset arrangements, yielding 27 captures. The original bundle provides the
robot, board and pieces. layout.json supplies marker geometry.

Changing --elevations is supported here. Azimuths, distance and resolution
are currently in the Python script. The P035 foreground experiment additionally
uses --evaluate-foreground, producing 36 captures over four arrangements.

## Proposed controlled sequence

The following are experimental proposals. Implementation and measurement are
required for conditions beyond the existing commands.

| Stage | Comparison | Hold fixed | Main question |
|---|---|---|---|
| 1 | One fixed camera, checker intersections versus four ArUco references | Same frames, camera, resolution, board and pieces | Does the reference improve board detection and address assignment? |
| 2 | Empty, initial, sparse and dense midgame positions | Camera and marker layout | How much does piece placement affect coverage? |
| 3 | Camera azimuth/elevation/distance sweep | Detector and resolution | Which mounting region is useful? |
| 4 | 800x600, 1280x960, 1920x1440 | Same rendered scene and FOV | How much benefit comes from resolution? |
| 5 | ArUco subpixel refinement on/off | Same saved images | How much comes from corner refinement? |
| 6 | Different measured marker spacing and sizes | Camera and detector settings | How does reference geometry affect error within the board? |
| 7 | One, two and three calibrated camera views | Scene, image budget and task | Does complementary visibility improve observation availability? |
| 8 | Known planar calibration grid or ChArUco fixture | Independently measured geometry | Can denser independent references improve calibration and validation? |
| 9 | Controlled marker occlusion, robot poses, lighting and lens distortion | Declared perturbation values | When does the system reject a frame or accept a bad mapping? |
| 10 | Piece heights and offsets, grasp-height measurements | Accepted board geometry | How much parallax remains in piece localization? |

For stages 1–6, reuse the same image files for detector comparisons wherever
possible. Capture a marker-equipped scene once and process each frame through
the checker mode and reference mode. Confirm the checker detector actually
finds the board. Evaluate both against the same independently projected points.

The current reference detector requires four configured markers. A study of
marker counts requires a separately specified estimator and validity policy.
All accepted-marker observations must retain their declared correspondences.

For multiple cameras, estimate one H per camera. A first experiment can select
an accepted view using marker residual and visibility, then compare with a
predeclared combination rule. Residual at fitted markers alone is insufficient
to prove accuracy inside the board. Simultaneous captures of the same static
scene allow visibility comparisons. Fusion for moving pieces additionally
requires timestamps, synchronization, camera calibration and a shared board
frame. 3D localization requires a geometry model or calibrated multiview
reconstruction.

## Distinguish grid meanings

- The green overlay is a visualization of the estimated coordinates. Drawing it
  supplies no additional image measurements.
- The checkerboard intersections are image measurements usable for fitting H.
- An independently measured physical grid provides validation points and may
  support calibration.
- A ChArUco board combines identified markers and checker intersections.
  Replacing or surrounding the playing board with one is a physical design
  decision. Its use has yet to be implemented in this pipeline.

## Metrics and reporting

Report accepted/total frames, orientation accuracy, 64-square assignment accuracy,
independent board-point errors (mean, median, p95, maximum), false acceptances
and processing latency. Keep rejected frames in coverage denominators.
Report piece-localization coverage and physical grasp error separately.

Use matched test images, fixed seeds for randomized scenes, saved configurations,
source/model/layout/image identities and held-out camera/lighting conditions.
Declare thresholds before the final evaluation. Repeated identical static
renders do not provide independent trials.

The P033 evaluator chooses the best D4 rotation/reflection using evaluation
truth. Its geometry score does not demonstrate orientation recognition.
The reference evaluator uses configured a8 orientation directly. For the article,
report orientation and geometric fit separately and adopt the same scoring
convention for both methods.

The historical P033 and P034 runs changed camera distance and resolution.
Their results illustrate development but do not isolate the causal effect
of ArUco. A controlled paired comparison is required for that claim.
